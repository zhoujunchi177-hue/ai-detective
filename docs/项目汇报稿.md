# MindTrace AI 推理档案 — 项目汇报稿

> 用途：向导师介绍本项目。全文按「讲得出来」组织，不是 API 文档。
> 每节末尾的「**可讲的一句话**」是现场可以直接说的版本。

---

## 0. 一句话定位

**一个把「真实未结悬案的公开档案」做成可调查空间的 AI 推理游戏。**
玩家不是在猜凶手，而是在整理可验证的时间点、公开证据与信息缺口 —— 并且游戏明确拒绝为现实悬案给出结论。

技术形态：Vue 3 + Spring Boot + MySQL + DeepSeek 的全栈应用，AI 深度参与对话与评估，但**评分与进度完全由 Java 决定**。

**可讲的一句话**：
> 这个项目想验证一件事 —— AI 能不能在一个「不允许它编答案」的场景里，当好一个受约束的角色。

---

## 1. 选题动机：为什么是「真实悬案 + 受限 AI」

三个动机，按重要性排序：

1. **AI 最危险的用法是「替用户对未知下定论」。** 现实未结悬案正好是这类问题的极端场景：网上有海量传闻，模型也倾向于给一个「听起来合理」的结论。所以我把「**不许下结论**」做成了系统的硬约束，而不是提示词里的一句请求。
2. **侦探题材天然适合检验「信息边界」。** 侦探游戏的核心机制就是「你只知道你知道的事」—— 这正好对应大模型最需要被约束的东西：上下文里不该有的信息，一个字都不能进去。
3. **内容可以真实。** 三个案件全部基于公开档案（警方通报、验尸官结论、FBI 公开材料、主流媒体档案），有真实可查的来源链接，不需要虚构世界观。

**可讲的一句话**：
> 我不是在做「AI 破案」，我是在做一个**约束测试场** —— 用侦探游戏这个壳，去压测 AI 的信息边界和角色一致性。

## 2. 产品形态与玩法闭环

### 2.1 玩家动线

```
注册/登录 → 悬疑档案馆（选案件）→ 调查台
   ├─ 时间线 / 人物 / 线索 / 证据链 / 文件 / 谜题 / 日志（七个标签页）
   ├─ 调查地图：逐个解锁地点，每次调查由 Java+MySQL 决定是否发现线索
   ├─ 询问 NPC：AI 对话，知识边界受限，可用关键词解锁特定档案
   ├─ 解谜题：时间线排序 / 证据链选择 / 假设判定
   └─ 我的推理 → 提交结案 → Java 算分 → AI 生成语言评价
→ 获得 EXP / 调查币 / 成就徽章 / 排行榜
```

### 2.2 三个关键设计

| 设计 | 做法 | 为什么这样做 |
| --- | --- | --- |
| **解锁完全由后端算** | 地点状态（`LOCKED`/`AVAILABLE`/`INVESTIGATED`/`COMPLETED`）由 Java 依据「已发现线索 / 已破解谜题 / 已调查地点」计算，前端只渲染 | 绕过前端直接打接口调查未解锁地点会被 400 拒绝。**状态不在客户端，就没有「改前端就通关」这条路** |
| **隐藏线索不计入完成度** | `is_hidden=1` 的线索是额外奖励，不算进 `clueCount` 与 `COMPLETED` 判定 | 否则玩家永远看不到「已完成」，完成度会永远差一点 |
| **证据板的关联由玩家建立** | 后端只校验「两端线索都属于本案且该玩家已发现」，**不判断这个关联是否成立** | 那是玩家的推理内容。AI 可以评价它是否自洽，但不替玩家下结论 —— 这条边界和「不给现实案件下结论」是同一条原则 |

### 2.3 内容规模（当前）

| 内容 | 数量 |
| --- | --- |
| 案件 | 3（水箱回声 / 剪影未署名 / 北加州的密文） |
| 真实来源链接 | 9 条 |
| 调查地点 | 14 个 |
| NPC | 7 个 |
| NPC 知识条目 | 17 条 |
| 线索 | 26 条（含隐藏线索） |
| 时间线事件 | 20 条 |
| 关系人 | 7 个 |
| 谜题 | 5 个（三种类型） |
| 成就徽章 | 4 枚（分 4 个稀有度档位） |

**可讲的一句话**：
> 玩法上最花心思的地方是**职责边界**：哪些事归 Java、哪些归 AI、哪些归玩家，我一开始就划清楚了。

## 3. 内容体系与伦理边界（这个项目的「立场」）

### 3.1 三个真实案件

| 编号 | 游戏标题 | 现实原型 | 年代 | 真实/改编/虚构比例 |
| --- | --- | --- | --- | --- |
| CASE-001 | 水箱回声 | Elisa Lam 案 | 2013 | 72 / 22 / 6 |
| CASE-002 | 剪影未署名 | 黑色大丽花案 | 1947 | 80 / 16 / 4 |
| CASE-003 | 北加州的密文 | 黄道十二宫杀手案 | 1968–69 | 88 / 10 / 2 |

### 3.2 REAL / ADAPTED / FICTIONAL 三级标注

界面上每一条内容都带类型标签：

- **REAL** —— 来自官方机构、主流媒体、档案机构或公开报告的事实
- **ADAPTED** —— 为调查体验整理的表达、顺序或解释边界
- **FICTIONAL** —— 游戏原创 NPC、谜题或推理节点

### 3.3 硬约束（写在系统里，不是写在文档里）

1. **AI 不得为现实悬案伪造结论。** 三个案件全部是未结案件，模型被要求只讨论游戏假设。
2. **AI 只能看到玩家已经获得的线索。** 未发现的线索不会进入提示词 —— 不是「叫它别说」，是**它拿不到**。
3. **NPC 只拿到自己那一份知识。** 同一个案件里「别人知道、他不知道」的信息，对 NPC 是不可见的。
4. **现实声明跟着分享图走。** 生成的分享图页脚固定写明「游戏推理不代表现实案件结论」—— 图会被转发到游戏之外，声明留在应用里等于没有声明。

**可讲的一句话**：
> 「不要让 AI 编」这句话如果只写在提示词里，是请求；写进数据流里，才是约束。我选后者。

## 5. AI 设计：三条链路，三种约束

### 5.1 三条链路的分工

| 链路 | 输入 | 输出 | 温度 |
| --- | --- | --- | --- |
| **NPC 对话** | 系统提示词 + 该 NPC 的知识边界 + 最近对话 | 纯文本（口语） | 0.55 |
| **推理分析** | 案件上下文 + 玩家已获线索 + 玩家假设 | 结构化 JSON（支持点/矛盾点/缺失证据/下一步/一致度） | 0.2 |
| **结案评价** | 案件上下文 + 玩家结案提交 | 结构化 JSON（评价语言） | 0.2 |

### 5.2 「让 NPC 像一个人，而不是一个知识库」

这是我在提示词上花时间最多的地方。玩家要的是**审问一个人**，不是**查一个知识库**。

「报告腔」曾经出现在**三个地方**，只改一处没用：

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 系统提示词 | 「范围之外必须明确说明」+「通常 120–300 字」 | 角色扮演指令：先回答、口语化、默认 2–6 句、不罗列方法论 |
| 降级回复（AI 不可用时） | 「就我所知……这是我愿意且能够说明的部分」 | 「嗯，这个我记得。」「这个我真不知道。」 |
| 喂给模型的 NPC 知识原文 | 「应先核对视频时间码与公开版本是否经过剪辑」 | 「电梯那段我看过好多遍……时间码好像不太对」 |

**第三条最容易被忽略**：提示词再像角色，如果喂进去的原文是顾问腔，模型复述出来还是顾问腔。

### 5.3 两个「提示词管不住，就用代码兜」的例子

- **标点全角化**：提示词已经要求全角标点，但实测 128 轮里仍漏 2 轮。排版是**确定性**缺陷，不该指望模型每轮都听话 → `TextStyle` 在代码里归一化，**且只在汉字相邻时替换**，所以 `12:30`、`1,000`、URL 里的半角符号一个都不会被动。
- **报告腔预警**：回复超过 200 字且玩家没要求详细时记 `log.warn`，但**只记日志、不裁剪内容** —— 裁掉尾巴可能正好删掉一条线索。要的是「能被发现」，不是「被截断」。

### 5.4 降级也是一条路径

未配置 Key 或上游故障时：返回 **HTTP 200 + `aiAvailable=false` + 口语化本地回复**，游戏进度照常由 Java 保存。降级是**设计好的状态**，不是错误。

**可讲的一句话**：
> 我把 AI 当成一个**可能失败的依赖**来设计，而不是一个必然可用的组件。

## 6. 工程实践：一个具体的性能优化案例

这部分适合讲「怎么用数据推翻自己的判断」。

### 6.1 起点：先造测量能力，再谈优化

原本后端**不解析响应的 `usage`**，手上一个真实 token 数字都没有。所以第一步不是改代码，而是造一把尺子：

- `deepseek-meter-proxy.mjs` —— 一个只做测量、不参与产品逻辑的 HTTP 代理，逐次记录 token 用量
- `measure-npc-tokens.py` —— 用**固定问题序列**跑，否则 before/after 不可比

### 6.2 第一个反直觉发现：「省 token」≠「省钱」

`deepseek-flash` 的计价是 **输入·缓存命中 0.02 / 输入·未命中 1.0 / 输出 4.0**（元每百万）—— **命中单价是未命中的 1/50**。

而 system 提示词是稳定前缀，几乎每轮都命中缓存。所以**压缩提示词省的是最便宜的那 2.8%**。实测把 system 从 1294 字压到 1063 字（−17.9%，44 条行为约束零丢失），**总费用被输出 token 的随机波动盖过，无法证明费用下降**。

> 结论：优化前先确认「你要优化的那一项，在总成本里占多少」。

### 6.3 第二个发现：真正的钱花在「玩家看不到的思考」上

响应里有 `reasoning_tokens`（思维链 token，按输出计费但**不展示给玩家**）：

| 链路 | 输出占成本 | 其中思考占比 |
| --- | --- | --- |
| NPC 对话 | 62% | 55.7% |
| 推理/结案 | **96%** | 约 67% |

### 6.4 关键转折：我两次判断错了，最后靠「直接问上游」找到答案

- **第一次错**：我发现玩家提问被发了两遍，就推断「删掉它能修复缓存前缀」，并写进了代码注释。**被数据推翻** —— 重复项永远在消息最末尾，从不落在两轮共享的前缀里。
- **第二次错**：我看自己的请求体里没有关闭思考的参数，就写下「**思考动不了，只能换模型**」。
  **这个结论也是错的** —— 我从「客户端代码」推断了「服务端能力」，这是无效推理。

正确做法是**写一个能力探针直接问上游**：

| 候选写法 | 结果 |
| --- | --- |
| 不传（基线） | 思考 148/181 token → 模型默认在思考 |
| `enable_thinking: false` | **上游接受但完全忽略** ← 第三方文档普遍推荐它，是个陷阱 |
| `thinking: {"type":"disabled"}` | **生效**，思考归零 |

### 6.5 结果

| 链路 | 优化前 | 优化后 | 降幅 |
| --- | --- | --- | --- |
| NPC 每轮 | completion 124.9 | **42.0** | **−66%** |
| NPC 每轮费用 | ≈849 单位 | **≈517** | **−39%** |
| 推理/结案每次 | ≈9282 单位 | **≈3400** | **−63%** |

**并且行为没有退化**（这才是能不能开的关键）：104 个单测全绿、7 个 NPC 共 128 轮真实对话 `failed=0/blocked=0`、提示词注入与越界提问仍然全部拒绝、单轮延迟从数秒降到 0.6–1.2 秒。

**但默认值我保持了关闭** —— 这是**行为变更**，而当时的任务授权是「优化提示词」，参数开关超出了授权范围。我把开关做好、把数字量准，**开不开留给使用者决定**。

**可讲的一句话**：
> 这段经历最有价值的不是省了 39%，而是**我两次把「自己的推断」当成「事实」写进了文档，又两次用数据把它删掉**。最后那句「我的代码里没写这个字段 ≠ 接口不支持这个字段」，是这轮最贵的教训。

## 7. 质量保障：分层验证，拒绝「假通过」

### 7.1 验证金字塔

| 层 | 工具 | 规模 | 关注点 |
| --- | --- | --- | --- |
| 单元测试 | JUnit 5 | **104 个用例 / 13 个类** | 纯函数逻辑、边界、约束不被误删 |
| 接口验收 | `verify-api.ps1` | **82 项** | 契约、拒绝路径、鉴权隔离 |
| 真实 AI | `verify-live-ai.py` / `verify-npc-voice.py` | 3 链路 + **7 角色 128 轮** | 多轮上下文、防注入、语气是否像人 |
| 页面验收 | 6 个 Playwright 脚本 | 64 + 29 + 11 + 12 + … | 渲染、交互、持久化、响应式 |
| 发布前专项 | RC 系列 4 个脚本 | 安全 / 并发 / 压测 / 性能 | 越权、竞态、奖励重复发放 |

### 7.2 三条自己定的验收纪律

1. **不为了让测试变绿而改断言。** 断言写错就改断言、并说清楚「错的是我，不是代码」。
2. **BLOCKED 不算 PASS。** 上游抖动导致的降级单独列出，既不算通过也不算失败；只有大面积降级才判失败。
3. **不把没实际执行的检查写成通过。** 每个验收脚本都有自检：源码里声明了几条断言、实际执行了几条，对不上就判失败 —— 因为**一条凭空消失的断言，会表现为「全绿」**。

### 7.3 一个具体的例子：验收脚本自己也会「假失败」

`source-link-check.mjs` 曾报「来源链接打不开」。查下来是**脚本读早了**（固定等待时长不够，读到的是上一个标签页），以及**读错了**（用「第一个新页面」定位，残留标签页会串位）。修好脚本后，原本 4 条「站点连不上」的警告也一起消失了。

> 脚本报错 ≠ 产品坏了。**先证明脚本是对的，再用脚本证明产品是对的。**

- 一键启动脚本（含等就绪 + 真实冒烟）

### 已知限制（都是「知道在哪、没动」）

| 限制 | 性质 |
| --- | --- |
| `/api/health` 在数据库不可用时仍返回 UP | 只反映进程活着 + 是否读到 Key，不探数据库。接监控需另加就绪探针 |
| `TIMELINE_MASTER` 徽章只能通过 CASE-001 解锁 | **内容缺口**，不是逻辑缺陷。补齐方式是为另两个案件各加一个时间线排序谜题，而不是放宽条件 |
| BGM 的 `tension` 音轨槽位是空的 | 类型/路径/配置都有它，但全项目没有一处触发它 —— 需要先设计「什么时候进入紧张状态」 |
| 测试覆盖率行 14.9% / 分支 30.7% | **有意为之**：纯函数走单测，服务与控制器走接口验收与端到端。只看总分没有意义，只看「部分覆盖行」 |
| 项目不使用 Mockito | Java 25 + byte-buddy 版本不兼容。因此所有可测逻辑都抽成 `static` 纯函数，反而让测试更结实 |

## 9. 后续规划

按优先级：

1. **补齐内容缺口**：为 CASE-002 / CASE-003 各加一个时间线排序谜题，解开 `TIMELINE_MASTER` 的单点依赖。
2. **把「紧张状态」设计出来**：什么交互该切到 `tension` 音轨（谜题失败？线索互相矛盾？），然后把空槽位接上。
3. **就绪探针**：把数据库连通性纳入健康检查，让它能真正接监控。
4. **评估开启「关闭思考」**：把默认值改成开启需要一次完整的行为复验（含 128 轮语气验收），并观察真实玩家是否觉得 NPC 变笨。
5. **扩充案件库**：内容生产是主要瓶颈，考虑把「案件建档」做成可配置的数据流程。

### 可能被问到的问题（备好答案）

- **「AI 会不会乱说？」** → 演示第 4/5 步；补充说明：未发现的线索**不进提示词**，不是靠叫它别说。
- **「评分是 AI 给的吗？」** → 不是。Java 计算完成度/线索完整度/时间线/逻辑得分，AI 只生成语言评价，且**不能修改分数与奖励**。
- **「真实案件这样做合适吗？」** → 三级内容标注 + 系统级硬约束 + 分享图带声明 + AI 只讨论游戏假设。
- **「为什么不用向量数据库 / RAG？」** → 当前信息量（26 条线索 / 17 条 NPC 知识）用确定性上下文装配更可控，而且**「不给什么」比「给什么」更重要** —— 检索式召回反而难以保证边界。
- **「成本和延迟如何？」** → 有完整测量工具链与真实数据（见第 6 节）。
