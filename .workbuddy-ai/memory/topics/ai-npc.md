# AI 链路、NPC 对话、Token 计量

> 从 `MEMORY.md` 拆出。改 Prompt / Agent / 上下文，或要优化 token 与费用时读这份。

## AI 链路约定
- **AI 调用必须留在事务之外**（见 `data-concurrency-auth.md`）。证据：`check-trx-boundary.sh` 峰值必须 0；3 并发推理时只读接口最慢 27.6ms。
- **8 种故障模式都必须优雅降级成 HTTP 200 + `aiAvailable=false` + 明确文案**，绝不向玩家抛 5xx。
- 提示词注入（索要系统提示词 / 隐藏线索 / 要求切换身份）由 `verify-live-ai.py` 覆盖，三种问法都必须被拒且**维持角色设定**。
- 真实模型可用性以 `GET https://api.deepseek.com/models` 为准，**不要照搬旧文档的模型名**。
- 防注入有**架构级**保障：`ContextBuilder` 只送 `disclosure_level='normal'` 的知识，未获得线索只传 type 不传内容。
- 消息顺序（`PromptBuilder.npcDialoguePrompt`）：`system → 注入上下文(buildNpcContextText) → 历史对话… → 玩家提问`。
  注意**玩家提问是最后一条**；上下文里那段【本轮】复述**不是**收尾锚点（后面还隔着最多 12 条历史）。

## NPC 对话约定（改动前先读）
- **「报告腔」有三个来源，必须一起改**：① `PromptBuilder.npcDialoguePrompt` 的 system 提示词
  ② `AgentService.fallbackNpc` 的降级文案 ③ **`npc_knowledge.content` 本身**。
  ③ 最容易漏：喂给模型的原文是顾问腔（「应先核对视频时间码、电梯控制逻辑」），提示词再像角色，模型复述出来还是顾问腔。
- 提示词硬性要求：先答后补、口语化、**最多 6 句（约 40~150 字）、不许拆成三段**、不罗列方法论、
  分层披露、接住上一轮上下文、只有确实不知道时才声明不确定、**始终第一人称**（不写「托雷斯叹了口气」这种第三人称旁白）、
  **标点一律中文全角**（半角 `, : ? ;` 混进中文一眼就像机器生成，`TextStyle` 还会二次兜底）。
  **7 条安全规则不动。任何改动必须过 `NpcPromptConstraintTest`。**
- **长度约束只记日志、不裁剪**：`AgentService.warnIfReportTone` 在 >200 字且玩家没要求详细时记 `log.warn`。
  裁掉尾巴可能正好删掉一条线索 —— 要的是「能被发现」，不是「被截断」。
  同理 AI 降级路径必须 `log.warn("NPC 对话降级为本地回复：…")`，否则查不出「这轮为何只有 13 字」。
- 改 `npc` / `npc_knowledge` 内容时，**必须同时改 `data.sql` 与 `database/migration-*.sql`**，改完跑 `verify-fresh-install.py`。
- 回归网 `python scripts/verify-npc-voice.py`，**必须 7 个 NPC 都跑**（`NPC_VOICE_NPC_ID=1..7`）：
  提示词是全局的，只验米娅等于「改了 7 个、只证了 1 个」。脚本按 NPC 档案驱动，每人四件套：
  `self_names`（抓旁白）/ `leak_markers`（**必须剔除他自己知道的词**）/ `part_a`（贴职责的必测序列）/
  `boundary_probes`（**固定必问**，否则随机抽样可能一条越界题都没抽到 → 那条检查会**空转通过**）。
  报告 → `artifacts/npc-voice-report[-npcN].html`（NPC 1 用原名，其余加后缀，互不覆盖）。
- 🔴 写「违规词表」检查时三个必守：
  ① **标记词必须来自知识边界之外**；
  ② **要扣掉玩家输入里出现过的词**（玩家问「凶手是谁？」，NPC 复述「凶手是谁……轮不到我说」是正确拒绝，却被子串「凶手是」判成下定论）；
  ③ 词表要**应用到每一个检查**，别只给泄露检查加护栏。
  本轮因此在「泄露 / 总结案件 / 下定论」三项上各误报过。
  **「拒绝是否维持角色」交给 `verify-live-ai.py` 的注入用例，别用启发式硬判。**
- 🔴 **给启发式词表配离线自检**：把每次真实误报的原句 + 必须命中的真阳样本写成表，
  在真实 AI 调用**之前**跑（毫秒级、不花 API）。误报原句是资产，别删。
- 已知非回归现象：米娅·托雷斯 24 轮里「这个我真」出现 3 次（阈值 5），脚本记 BLOCKED，非 FAIL。

## Token 计量与提示词压缩（2026-09-21）
**`DeepSeekService` 不解析响应里的 `usage`** → 手上一个真实 token 数字都没有。要优化先得量。

### 工具
- `scripts/deepseek-meter-proxy.mjs`：HTTP 代理 9098 → `api.deepseek.com`，`Authorization` 原样透传（用的是后端自己的真实 Key），
  记录每次 `usage` 到 `.runtime/token-meter.jsonl`。**必须记 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`**，否则会得出错误结论。
- `scripts/measure-npc-tokens.py --label X`：固定 8 个问题（否则 before/after 不可比），注册全新账号，输出归因表。
- **跑法**：`node scripts/deepseek-meter-proxy.mjs`（后台）→
  `OVERRIDE_BASE_URL=http://127.0.0.1:9098 python scripts/start-backend-with-key.py`
  （**只覆盖 base-url、不覆盖 api-key**，这样用注册表里的真实 Key）。跑完切回真实 API 并用三项证据确认。

### 三个必须分开看的数字
1. **token 消耗** → 看**固定成本 b**，别看 prompt 均值。`prompt = a × 历史字符 + b`，
   b 是与历史无关、每轮必付的部分（system + 注入上下文 + 问题）。
   **历史长度取决于上一轮回复多长，而回复长度是随机的**：同一份提示词跑两次，回复均值 92 字 vs 64 字（差 30%），
   prompt 均值跟着在 1157~1208 之间晃。用均值比较会把提示词效果和回复噪声混在一起。
2. **费用** → 看真实价目。`deepseek-flash` 空闲档（周一至周五 9:00-12:00、14:00-18:00 之外）：
   **输入·缓存命中 0.02 / 输入·未命中 1.0 / 输出 4.0 元每百万** → **命中单价是未命中的 1/50**。
3. **缓存命中率** → 改提示词会把缓存打冷，第 1 轮命中率为 0。那是**一次性**重建成本，比较时要剔除。

### 实测结论（NPC 1，8 轮，真实 AI）
- 提示词压缩：system **1294 → 1063 字（-17.9%）**，注入上下文 535 → 478 字；**44 条行为约束逐条核对零丢失**。
- **固定成本 1133 → 968 token/轮（每轮少 165，-14.5%）**；斜率 a 不变（历史部分没动过）→ 归因自洽。
- **费用结构（压缩前）：缓存命中输入 2.8% / 缓存未命中输入 34.8% / 输出 62.3%**
  → 压缩动的 system/上下文几乎全在「命中输入」里，**只占成本 2.8%**；即使压到 0 字，费用上限也只省 2.8%。
  **「省 token」和「省钱」在这里不是一回事。**
- **输出占 62%，其中 55.7% 是玩家看不到的「思考」**（4 轮实测 `completion_tokens_details.reasoning_tokens`）：
  completion 合计 540 = 思考 **301（55.7%）** + 可见回复 239 → 折算总成本 **思考 ≈35% / 可见回复 ≈28%**。
  第 3 轮思考 160 而可见回复仅 55 → **思考量随问题难度变化，与回复长度不同步**（「回复短=便宜」是错的）。
  `chat-max-tokens=1200` 而实测 completion 只有 96~215 → **上限不是瓶颈，别去调它**。
- **⚠️ 上面那句「目前动不了」已被推翻（2026-09-21）：思考能从请求里关掉。**
  我原先只看了自己的请求体就下结论，**没去问上游** —— 「我的代码里没写这个字段」≠「接口不支持」。
  - **上游只认** `thinking: {"type":"disabled"}`。网上与第三方文档普遍推荐的
    `enable_thinking: false` **会被接受但完全忽略**（思考照旧）—— **是个陷阱**。
    验证工具：`scripts/probe-thinking-param.py`（读注册表 Key，**只打印长度不打印内容**，三种写法各发一次）。
  - 开关：`deepseek.disable-thinking` / `DEEPSEEK_DISABLE_THINKING`，**默认 false = 不改行为**。
    请求体组装已抽成 static `buildPayload()`（好让测试不用 Mockito），
    由 `DeepSeekThinkingSwitchTest` 4 条钉住「用哪个字段」「默认不发」「绝不发 enable_thinking」。
  - 单发对照（同一句话各发两次）：对话 210 → 12；JSON 463 → 41，**仍是合法 JSON**。
    少掉的全是玩家看不到的思考，**可见正文长度基本不变**。
  - **JSON 链路端到端实测**（`measure-reasoning-tokens.py`，3 次推理审阅 + 1 次结案评估，全新账号）：
    prompt 4676→4576、输出 **8928 → 2695（−70%）**、思考 **6001 → 0**、
    费用 **37126.6 → 13599.8（−63%）**，即每次 **≈9282 → ≈3400**。
    4 次全部 `http=200 / aiAvailable=true`，`confidence` 12/45/22 有区分度，结案报告正常产出 → **功能未坏**。
    注：两次的缓存命中分布不同（3328 vs 1792，因第 1 次与结案那次本就无共享前缀），
    同口径折算约 **−65%**；稳健的实测事实是**输出 −70%**。
  - 端到端（8 轮固定问题，NPC 1）：completion **124.9 → 42.0（−66%）**，
    每轮费用 **≈849 → ≈517（−39%）**。降幅小于 completion 降幅，因为**输入没变且占大头**。
  - **行为未退化**：`mvn test` 104/104；`verify-npc-voice.py` ×7 `failed=0/blocked=0`
    （开思考时 NPC 1 还有 `blocked=1`）；`npc-chat-ui-check.mjs` 11/11；
    注入与越界提问仍拒绝、不泄露、不给现实案件下定论；延迟从数秒降到 0.6~1.2 秒。
  - **但默认仍是 false**：属行为变更，且用户当时的授权是「优化**提示词**」，开不开由用户决定。
  - 附注：`json-max-tokens=8000` 原本是**为思考留空间**才开这么大，关思考后显得宽松，但它是上限不是消耗，留着无害。
- **滑窗满之后 cacheMiss 上升，但「改截断能省 25%」是错的**（4 次独立运行）：
  `MAX_RECENT_MESSAGES=12`，**窗口未满 cacheMiss ≈ 140~250/轮；窗口满后 ≈ 390~485/轮**。
  **⚠️ 原先的解释「滑窗让前缀每轮断一次」已被实测推翻**：若前缀真的延续，
  第 N+1 轮 `cacheHit` 应 ≈ `floor(第 N 轮 prompt / 128) × 128` —— **4 次运行都只有 2/7 轮成立**。
  且 `cacheHit` 本就只覆盖 system+上下文（历史几乎从不进缓存，**窗口没满时也一样**）；
  把轮间隔从约 1.7 秒拉到 **12 秒**（`--delay 12` 模拟真人）**命中量毫无变化**。
  → 可归因于滑窗的只有约 **1 个 128 量化档（≈128 token）**，其余只是「输入本来就变长」。
  **上游缓存的命中边界行为目前没有可靠模型**，别基于「改截断能省很多」去动它；真要动先量。
- **缓存实际只覆盖 system + 上下文**（2026-09-21 补量，纠正了原先的模糊认识）：
  `cacheHit` **恒为 128 的整数倍**（768/896/1024/1152/1280）→ 缓存按 **128 量化**；
  命中量基本就等于 `system + 注入上下文`（压缩后 1541 字 ≈ 896 token）。
  **历史部分根本没进缓存** → 别指望「历史越长、缓存越省」。检验脚本 `scripts/check-cache-claim.py`。
- **提问曾被发两次（已修，`ContextBuilder.stripCurrentQuestion`）**：
  `ChatService` 为了「刷新不丢问题」在调 AI **之前**落库提问，于是 `recent()` 最后一条就是本轮提问，
  而 `PromptBuilder` 又追加一次 `playerQuestion` → 同一句话发两遍。
  修法只删「最后一条 && role=user && 与提问逐字相同」的那条，**信息量不变**。
  效果：首轮 prompt **1139 → 972**，8 轮合计 **10662 → 9221（-13.5%）**，历史条数上限 **12 → 11**。
  **⚠️ 我曾以为它还能「修复缓存前缀」—— 推断被实测推翻**：重复项永远在**最末尾**，
  下一轮同一位置必然换成上一轮回复，它**从不落在共享前缀里**。检验法：
  「hit = floor(上一轮 prompt/128)×128」在 8 轮里只对了 2 轮。
  **去重本身只省约 7~9 token/轮（提问平均 13 字），很小** —— 首轮 -167 里绝大部分来自 system 与【本轮】压缩。
  保留它是因为零风险、且模型看到的话更接近真实对话，**别把它当成绩汇报**。

### 压缩提示词的正确做法
- **把约束固化成会进 CI 的测试**，不要只做一次性脚本：`NpcPromptConstraintTest`
  （44 条约束 + 7 条安全规则 + 字数上限 + 消息顺序不变量）。
  字数变少一眼能看出来，**约束丢了看不出来**。
- **压缩时先做 diff 复核再定稿**。关键词清单会漏掉细微语义 —— 本次 diff 才发现删过头了：
  「【怎么说话】这一节比"说得严谨"更重要」（语气优先于严谨的优先级指令）、
  「写完自己数一遍，超了就删掉最后几句」（支撑最脆弱的长度约束）都是有行为价值的，不是重复，已恢复。
- **提示词文本只留一个真源**。本次先手写 `new-system-block.txt` 再去拼 Java，
  改了 `prompt-new.txt` 忘了同步 → 拼进去的还是旧文本（脚本报了字数不符才发现）。
- 用**行号 + 首尾锚点**拼接，别手敲 `old_string`（40 多行中文，差一个空格就匹配失败或改错位置）。
  **别漏结尾的 `;`**（`"""))` 少个分号 → 编译错误「需要';'」）。
- 行为复验三层缺一不可：`mvn test`（**100/100**）+ `verify-npc-voice.py` × 7 角色（128 轮，failed=0）+ `npc-chat-ui-check.mjs`（11/11）。
