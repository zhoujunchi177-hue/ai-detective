### 关键判定方法（本轮最有价值的产出）

**`curl` 通了不等于浏览器能开，`curl` 不通也不等于链接死了。** 实测：
- `www.bbc.com` 被 **DNS 污染**，解析到 `173.252.108.21`（Meta 的 IP 段）

所以可达性判定必须分三类，且**至少两条通路交叉验证**（脚本探测 + 真实浏览器，必要时查 Wayback）：
| 状态 | 判据 | 是否算失败 |
|---|---|---|
| dead | 404 / 410 | 是 |
| blocked | 401 / 403 / 429 | 否（多半是反爬） |
| unreachable | 超时 / 重置 | 否（本机网络限制） |

### 找到并修复的 4 个真实缺陷

1. **未登录返回 403 而不是 401** → 前端 `client.ts` 只认 401，
   令牌过期时不清理本地令牌、不跳登录页。修：`SecurityConfig` 显式设
   `authenticationEntryPoint`(401) / `accessDeniedHandler`(403)，回 ApiResponse 同结构 JSON。
   （同一个「未登录」，走过滤器链是 403、走到控制器是 401 —— 不一致本身就是 bug。）
2. **参数类型错误 500 + 泄露内部实现**：`/api/cases/abc`、`?npcId=abc` 返回 500，
   响应体里带 `Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'`。
   修：`GlobalExceptionHandler` 补 4 个 400 分支，兜底不再回传 `exception.getMessage()`。
3. **谜题答案超长 500**：`user_puzzles.answer` 是 VARCHAR(1000) 但 DTO 无长度约束。修：`@Size(max=1000)`。
4. **并发写竞态**（线索解锁 / 谜题提交 / 证据关联都是「先查后写」）。

### 并发修复的关键教训（最值得记住）

- **`INSERT IGNORE` 会让情况变糟。** 第一版把「先查后插」改成 `INSERT IGNORE`，
  实测 `DeadlockLoserDataAccessException`（500）—— 它在唯一键上取共享锁，两个事务互等。
  原来的唯一键冲突至少还是 400。
- **最终修法**：`SELECT id FROM users WHERE id = ? FOR UPDATE` 锁用户行，
  把同一玩家的并发写串行化（不同玩家互不影响），`INSERT IGNORE` 留作兜底。
- **🔴 加锁必须是事务里的第一条普通 SELECT。** REPEATABLE READ 的读视图在事务内
  第一条**普通读**时建立。先跑 `requireCase`（普通 SELECT）再抢锁 → 等锁期间别的事务已提交，
  但本事务快照早已固定，后面照样读到「没有记录」，**加了锁也不管用**。
  在 `PuzzleService.submit` 上实测复现过（第一版锁放晚了，压测 C 场景 8 轮全挂）。
- 涉及文件：`UserMapper`(新增 `lockById`)、`UserClueMapper`(新增 `insertIgnore`)、
  `ClueUnlockService`、`PuzzleService`、`EvidenceBoardService`。

### 验收脚本自身的两处「假失败」（不是产品 bug，但会误导人）

1. `source-link-check.mjs` 用固定 `waitForTimeout` 等标签页切换。玩家数据变多后
   固定时长不够 → 读到**上一个**标签页 → 报「文件标签页 0 条来源」。

## 修复「按 README 依次启动后登录失败」（用户实际反馈）

用户反馈：用 PS 依次跑三个启动脚本后，登录显示「服务器连接失败」。

### 先确认这不是产品缺陷

- 全项目 **没有任何一处**产生「服务器连接失败」这句文案 —— 前端错误提示是
  `ElMessage.error((error as Error).message)`，直接透传 axios 的原文。
  所以这句话来自**浏览器**，意味着页面压根没加载出来（前端服务没起来）。
- 三个组件单独实测全部正常：`vite dev` 正常（页面 200、`/api` 代理通、登录成功）、
  `vite preview` 正常、后端正常、MySQL 正常。**所以不是代码问题，是启动方式问题。**

### 根因（三条，全部实测复现）

1. **后两个脚本是前台常驻进程，永不返回。**
   `start-backend.ps1` 结尾是 `mvnw.cmd spring-boot:run`，`start-frontend.ps1` 结尾是
   `npm run dev` —— 都会一直占着窗口。所以「依次执行」最多走到第 2 步，
   **前端从未启动**，浏览器打开 5173 自然连不上。

### 顺带修掉一个 PS 5.1 编码坑

## NPC 对话「报告腔」改造

### 问题

玩家反馈 NPC 的回答像 AI 助手 / 法律顾问，不像一个角色。原话：
「我只能给你一个谨慎的框架……」「我不把『记得』当作证据……」「我的职责是……」
「我能确认的只有……」—— 沉浸感被破坏。

### 根因：三处必须一起改，只改提示词没用

1. `PromptBuilder.npcDialoguePrompt` 的 system 提示词：规则 2 强制
   「范围之外必须明确说『我没有接触过这部分信息』」，规则 6 要求「通常 120-300 字」

2. `AgentService.fallbackNpc`（未配置 Key / AI 挂掉时的降级）：

## 自查「我的检查项有没有空转」（第五轮）

固定了越界探针之后，我反过来问：**其余检查项在最终运行里真的检到东西了吗？**
抽查「重复介绍 / 有没有用上一轮上下文」这条 —— 它最容易变成空转
（如果三轮回复本来就都不一样，这条检查等于没验）。

米娅「同一个问题连问三次」的实际输出：

| 轮次 | 回复开头 | 与前轮相似度 |
| --- | --- | --- |
| ① | 「**这个我刚说过**，我也想知道。可能设备卡了，也可能有人一直在外面按……」 | — |
| ② | 「**你刚才也问过这个**。我还是那句：不知道。……」 | 0.51 |
| ③ | 「**我刚回答过两遍了**。还是不知道，没有新东西。……」 | 0.13 / 0.25 |

结论：**检查项非空转**（三轮彼此差异明显，相似度全在 0.72 阈值下），
且「记忆感」达标 —— 三轮都主动承认「这个我说过了」，而不是假装是新信息。
①② 的 0.51 是因为**事实本来就只有那两条**（设备卡了 / 有人按），
重复事实是对的，重要的是它承认重复过 —— 这正是用户要的效果。

> 教训：**给检查项做「非空转」自查**和给脚本做自检是两件事。
> 前者问「这条检查有没有拿到能失败的输入」，后者问「这条检查有没有被执行」。
> 空转的检查比不写更糟 —— 它会给出虚假的安全感。

## 三、结论：三个数字必须分开看

**① token 消耗 —— 达成。** 但**不能用 prompt 均值比较**：
`prompt = a × 历史字符 + b`，而历史长度取决于上一轮回复多长，回复长度是随机的 ——
同一份提示词跑两次，回复均值 **92 字 vs 64 字（差 30%）**，prompt 均值跟着在 1157~1208 晃。
改拟合后比**固定成本 b**：

| | 固定成本 b | 斜率 a | R² |
| --- | --- | --- | --- |
| 压缩前 | **1133.0** token/轮 | 0.662 | 1.000 |
| 压缩后 | **968.3** token/轮 | 0.667 | ~1.000 |

→ **每轮少 165 token（-14.5%）**，斜率不变（历史部分没动过）→ 归因自洽。

> 基线文件被我自己的 `cp` 覆盖了（测量脚本每次会先删文件），靠计量代理逐轮打印的
> `prompt/cacheHit/cacheMiss/历史字符` 重建，并用上一会话独立换算出的 b=1134.2 交叉校验
> （实测 1133.0，偏差 0.1%）确认转录无误。

**② 费用 —— 无法证明下降，而且这是结构性的。**
`deepseek-flash` 空闲档：输入·缓存命中 **0.02** / 未命中 **1.0** / 输出 **4.0** 元每百万
→ **命中单价是未命中的 1/50**。而 system 提示词是稳定前缀，**几乎每轮都命中缓存**。
压缩前费用结构：

| 项目 | 占比 |
| --- | --- |
| 缓存命中输入 | **2.8%** |
| 缓存未命中输入 | 34.8% |
| 输出 | **62.3%** |

我压的正是那 2.8%。**即使把 system 压到 0 字，费用上限也只省 2.8%。**
实测 8 轮总费用被输出 token 的随机波动（±20%）盖过 —— **「省 token」和「省钱」在这里不是一回事**。

**③ 顺手发现一个真实浪费：滑窗截断破坏前缀缓存**（3 次独立运行一致复现）。
DeepSeek 按「前缀完整匹配」命中；`MAX_RECENT_MESSAGES=12` 每轮砍掉最老一条 → 前缀就断一次。

| 状态 | cacheMiss |
| --- | --- |
| 窗口未满（历史 1~11 条） | ≈ 140~250 token/轮 |
| 窗口满（历史 =12 条） | ≈ 390~485 token/轮 |

每轮多付约 200 个未命中 token，折合每轮成本约 25%。
不截断能让前缀完美延续，**但 token 数量会上升** —— 与用户目标相反。
这是个取舍点，已把实测数字写进 `ConversationMemory` 常量旁边的注释，**未擅自改动**。

## 七、第七轮：提问被发两次（去重）+ 一个被数据推翻的推断

### 怎么发现的
复查上一轮的原始计量记录时，看到第 8 轮的 `breakdown` 是
`[1063, 478, 61, 15, 69, 17, 59, 10, 50, 14, 66, 12, 75, 14, 14]`
—— **末尾两条一模一样**（都是 14 字），也就是同一个提问。

### 成因（读代码确认，不是猜）
`ChatService.chat()` 第 71 行 `saveImmediately(user)` **先**落库，
第 75 行才 `agentService.npcReply()`。所以 `recent()` 拿到的最后一条**就是本轮提问**，
而 `PromptBuilder` 第 53 行又 `messages.add(..., context.playerQuestion())` 追加一次。
→ 同一句话发了两次。

### 修法
`ContextBuilder.stripCurrentQuestion(messages, question)`：只删
「最后一条 && role=user && 与 question 逐字相同」的那一条，`List.copyOf` 返回。
放在 `ContextBuilder`（历史的生产者）而不是 `PromptBuilder`，
因为不变量属于「recentMessages 不含本轮提问」。
写成 `static` 纯函数 → 不用 Mock 就能单测（本项目 Java 25 + byte-buddy 禁 Mockito）。

### 实测（8 轮固定问题，NPC 1）
| | 首轮 prompt | 8 轮合计 | 历史条数上限 |
| --- | --- | --- | --- |
| 改前 | 1139 | 10662 | 12 |
| 改后 | 972 | 9221（-13.5%） | 11 |
线上证据：逐轮打印计量记录里的 `breakdown`，末尾「连续两条相同 role=user」的轮数 = **0**
（改前第 8 轮是 `… a6(75), q8(14), q8(14)`）。历史条数上限也从 12 变成 11。

### ⚠️ 我说错了一次，被自己的数据打脸
我推断：「重复项在最末尾 → 打断缓存前缀 → 删掉它，本轮输入就成为下一轮的前缀 → 缓存整段命中」。
**这个推断是错的。** 写了个检验脚本（已落成 `scripts/check-cache-claim.py`，不再放 gitignore 目录）：
如果推断成立，第 N+1 轮的 `cacheHit` 应 ≈ `floor(第 N 轮 prompt / 128) × 128`。
结果 **8 轮只对了 2 轮**。

错在哪：重复项永远在**最末尾**，而下一轮在同一位置必然换成上一轮的回复
（`qN, qN` → `qN, aN`）—— 它**从来不属于两轮共享的前缀**，删掉它不会让可命中的前缀变长。

### 顺带量到的两个新事实
- `cacheHit` **恒为 128 的整数倍**（768/896/1024/1152/1280）→ 缓存按 **128 量化**。
- 命中量**基本就等于 `system + 注入上下文`**（压缩后 1541 字 ≈ 896 token），
  **历史部分根本没进缓存** → 「历史越长、缓存越省」的直觉在这里不成立。

所以去重的真实收益 = **约 7~9 token/轮**（提问平均 13 字），很小。
首轮 -167 里绝大部分来自 system 与【本轮】的压缩，不是去重。
保留它的理由：零风险、信息量不变、模型看到的话更接近真实对话。
**已把错误的推断从 `ContextBuilder`、`NpcHistoryDedupTest` 的注释里删掉并写明推翻过程** ——
留着一条假注释比没有注释更糟。

### 我自己的测试又纠正了我一次
`NpcHistoryDedupTest` 里我写 `assertEquals(4, messages.size())`，实际是 5 条
（system 1 + 上下文 1 + 历史 2 + 提问 1）。**算错的是我，不是代码。**
改成断言完整的角色序列 `[system, user, user, assistant, user]`，
比裸数字更能说明结构。另外把 `NpcPromptConstraintTest` 的 `@DisplayName` 里
写死的「41 条」改成实际的 44 条。

## 八、第八轮：用节奏对照推翻了「滑窗破坏前缀」的解释

### 起因：我发现自己的测量方式可能有问题
上一轮留下的记录是「滑窗截断破坏前缀缓存，每轮多付约 200 token，占成本约 25%」。
但我意识到：**我的测量是 1~2 秒一轮跑的**，而 DeepSeek 的缓存要数秒才建好。
那么「历史不进缓存」可能只是**我的节奏造成的假象**，而不是滑窗造成的。
真实玩家两条消息间隔 10~30 秒。**这个疑点必须用对照实验排除。**

### 做法
给 `scripts/measure-npc-tokens.py` 加了 `--delay`（轮间等待秒数），
跑了一次 `--delay 12` 的「模拟真人节奏」对照（同样 8 轮固定问题、同一角色）。

### 结果：节奏完全没有影响
| | 全速（≈1.7 秒/轮） | 真人节奏（12 秒/轮） |
| --- | --- | --- |
| 命中预言成立 | 2/7 | 2/7 |
| cacheHit 取值 | 768 / 896 / 1024 | 768 / 896 / 1024 |
| 命中中位数 | 896 | 896 |
| system+上下文 | 1541 字 ≈ 896~1024 token | 同 |

→ **「缓存还没建好」这个解释也被推翻。** 历史部分就是基本不进缓存，与节奏无关。

### 于是「滑窗破坏前缀」这个解释也站不住
因为**窗口没满时**（前缀完整延续）它也不进缓存。加上 4 次运行命中预言都只对 2/7，
我原先写进 `ConversationMemory` 常量的解释（「每轮砍掉最老一条 → 前缀断一次」）**是错的**。

可归因于滑窗的只有约 **1 个 128 量化档（≈128 token）**，其余只是「输入本来就变长了」。
上游缓存的命中边界行为**目前没有可靠模型** —— 我把这句话写进了注释，
**而不是再编一个顺口的解释**。

### 本轮改动（除测量脚本外都不是行为改动）
- `ConversationMemory.MAX_RECENT_MESSAGES` 常量注释：删掉错误解释，写明推翻过程与检验方法
- README「顺带发现」小节：标题从「会破坏前缀缓存」改为「cacheMiss 会上升（但别以为改它能省 25%）」
- `topics/ai-npc.md`、`MEMORY.md`、技能 §20.4/§20.9：同步修正
- `scripts/measure-npc-tokens.py` 新增 `--delay`（只影响测量脚本，不影响产品）

### 结论：这条链路上已经没有「既安全又显著」的省 token 空间了
| 杠杆 | 可省 | 代价 |
| --- | --- | --- |
| 压缩提示词 | ≤2.5%（命中价输入） | 已接近极限，再压只省最便宜那部分 |
| 改截断 / 修缓存 | ≈128 token/轮，且机制不明 | 投机，原解释已证伪 |
| **减少输出** | **最大（占成本 62%）** | **属行为变更**（思考模式 / 长度目标），需单独评估 |

**下一步该由用户决定** —— 剩下能动的基本都是行为变更，不该我单方面改。

### 教训
1. **测量节奏本身是变量。** 快节奏测量很容易把「节奏假象」当成「结构必然」。
2. **同一个现象我给过两个解释，两个都被数据推翻。** 现象成立 ≠ 解释成立。
3. **解释不了就写「没有可靠模型」**，别留一个顺口的结论在代码里。

## 九、第九轮：把「输出贵」拆成「贵在思考」和「贵在回复」

### 起因
上一轮我的结论是「真正的杠杆是输出（62%），但属行为变更，需用户决定」。
这句话太笼统 —— **它没回答「贵在思考还是贵在回复」**，而这两者可动性完全不同：

| --- | --- | --- | --- |

### 但结论是「动不了」
`DeepSeekService` 请求体只发 `model / messages / temperature / max_tokens / response_format`，

不再说「输出贵，你决定」，而是给出：可省上限 **约 35%**；手段是**换模型**（没有参数开关）；

**我的建议是不换**：本次 7 角色 128 轮对话验收 failed=0，
这个质量正是靠这段思考撑起来的，用 35% 的钱换对话质量下降不划算。
但这是商业决策，**我只把数字摆清楚，不替他拍板**。

### 教训
1. **「贵在 A」还不够，要拆到「贵在 A 的哪一部分」** —— 可动性往往取决于这个拆分。
2. 代理只留「当时够用」的字段，就会在下一个问题面前重跑一遍 ——
   加 `rawUsage` 一次留全，比每次补一个字段便宜。

### 教训
1. **「我的代码里没有这个字段」≠「接口不支持这个字段」** —— 上一节就是在这里翻车的。
   涉及外部能力，**先去问上游**，别把「我没写」当成「它没有」。
2. **文档会错，而且要自己验证**：`enable_thinking` 被广泛推荐，实测完全无效。
